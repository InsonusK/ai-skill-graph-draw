# ТЗ: CLI-приложение для отрисовки/актуализации диаграмм связей между markdown-файлами

Статус: черновик для реализации агентом
Дата: 2026-07-07

## 1. Цель

Создать Python CLI-приложение, которое строит диаграммы связей между markdown-файлами
(в первую очередь — графы зависимостей между `*.skill.md` файлами в этом репозитории)
и сохраняет их в виде файлов диаграмм (в первой версии — Obsidian Canvas `.canvas`).

Приложение должно уметь не только рисовать граф с нуля, но и **актуализировать**
уже существующую диаграмму: при повторном запуске не должно "случайно" уничтожать
ручную работу пользователя (перемещённые в Obsidian узлы) — обновляться должно
только то, что реально изменилось.

## 2. Область применения

- Источник данных — markdown-файлы с YAML frontmatter (пример: `skills/dotnet/architecture/artifacts/solutions/🧩validated/*.skill.md`).
- Связи между файлами задаются полем во frontmatter, содержащим список wiki-ссылок
  (пример: `depends_on` в `solution-value-objects-and-rules.skill.md`).
- Результат первой версии — файл Obsidian Canvas (`.canvas`, JSON).
- Приложение — CLI-утилита без демона/watch-режима. Регулярный запуск (по расписанию,
  по git-хуку и т.п.) — ответственность внешнего планировщика, не этого приложения.

### Вне рамок первой версии
- Watch/daemon режим.
- UI/GUI.
- Форматы вывода, отличные от Obsidian Canvas (интерфейс для них закладывается, но не реализуется).
- Фильтры ссылок, отличные от "поле frontmatter" (интерфейс закладывается, реализация — только `frontmatter_field`).
- Автоматическое обнаружение циклов с "красивым" визуальным разрешением — только базовая защита от бесконечных циклов при расчёте слоёв.

## 3. Термины

| Термин | Значение |
|---|---|
| Задача (task) | Один запрос на отрисовку/актуализацию одной диаграммы: свой набор файлов, свои фильтры ссылок, свой output |
| Узел (node) | Один markdown-файл, попавший в диаграмму |
| Ребро (edge) | Одна связь между двумя узлами, найденная одним из фильтров ссылок |
| Фильтр ссылок (link filter) | Правило, по которому в файле ищутся связи с другими файлами |
| Граф задачи | Итоговый набор узлов и рёбер для одной задачи, до раскладки координат |
| Раскладка (layout) | Присвоение координат (x, y) узлам графа |
| Кэш задачи | Сохранённое состояние последнего успешного расчёта задачи (хэши + позиции узлов) |

## 4. Архитектура — компоненты

Каждый компонент — отдельный модуль/класс с узкой ответственностью и явным интерфейсом,
чтобы части можно было заменять независимо (особенно: фильтр ссылок, writer, layout).

```
CLI / Entrypoint
   └─> Config Loader
          └─> Orchestrator (на каждую задачу)
                 ├─> Source Collector       (собрать md-файлы по фильтру)
                 ├─> Cache Manager          (проверка кэша по хэшу файлов / хэшу связей)
                 ├─> Link Filter[]          (pluggable, извлечение ссылок из файла)
                 ├─> Metadata Extractor     (извлечение id/label/анкора из файла)
                 ├─> Link Resolver          (сопоставление ссылки → узел графа)
                 ├─> Graph Builder          (сборка Node/Edge графа задачи)
                 ├─> Diff Engine            (сравнение с предыдущим графом из кэша)
                 ├─> Layout Engine          (pluggable, расчёт координат для новых/изменённых узлов)
                 └─> Format Writer          (pluggable, запись результата, напр. ObsidianCanvasWriter)
```

### 4.1 CLI / Entrypoint
- Разбирает аргументы командной строки.
- Поддерживает два режима запуска:
  1. **Разовая задача через аргументы** — все параметры задачи передаются флагами.
  2. **Пакет задач через конфиг** — `--config path/to/config.yaml`, в конфиге описан список задач.
- Оба режима порождают одинаковую внутреннюю структуру `RenderTask` и передают её в Orchestrator.
- Флаг `--force` — игнорировать кэш, полностью пересчитать и перезаписать результат.
- Флаг `--task-id <id>` (только с `--config`) — выполнить не весь пакет, а конкретную задачу(и) из конфига.

### 4.2 Config Loader
- Загружает YAML-конфиг, валидирует обязательные поля (см. раздел 6).
- Ошибка валидации одной задачи не должна останавливать весь пакет — невалидная задача
  логируется как пропущенная, остальные выполняются.

### 4.3 Source Collector
- Вход: `source.include` (список glob-паттернов), `source.exclude` (опционально).
- Выход: отсортированный список абсолютных/repo-relative путей к markdown-файлам.
- Сортировка обязательна — чтобы хэш набора файлов был детерминированным между запусками.

### 4.4 Link Filter (pluggable, интерфейс)
```
class LinkFilter:
    name: str          # имя фильтра, уникальное в рамках задачи (напр. "depends_on")
    style: EdgeStyle    # цвет/label/линия для рёбер этого фильтра

    def extract(self, file_content, frontmatter) -> list[RawLink]:
        """Возвращает список найденных сырых ссылок (текст wiki-ссылки) в файле"""
```
- Реализация v1: `FrontmatterFieldLinkFilter(field: str)` — читает список wiki-ссылок
  (`[[path|alias]]`) из указанного поля frontmatter (напр. `depends_on`).
- В одной задаче может быть **несколько** фильтров одновременно (напр. `depends_on` и `extends`
  с разными стилями рёбер на одной диаграмме). За отсутствие смыслового дублирования между
  фильтрами отвечает пользователь конфигурации, не приложение.
- Будущие реализации (вне v1, но интерфейс должен это допускать без изменения ядра):
  поиск wiki-ссылок по всему телу файла, поиск по конкретной секции/regex.

### 4.5 Metadata Extractor
- Вход: файл + его frontmatter.
- Выход: `NodeMetadata { id, label, subpath }`.
- `id` — стабильный идентификатор узла. **По умолчанию — repo-relative путь к файлу**
  (не хэш) — так узел не "теряет" свою идентичность при незначимых изменениях контента,
  и merge с предыдущим графом (см. 4.7) становится тривиальным сравнением по id.
- `label` — берётся из указанного в конфиге поля frontmatter (по умолчанию `name`).
- `subpath` — опциональный фиксированный анкор, добавляемый к file-ссылке узла в Canvas
  (в примере `Untitled.canvas` это `#Capabilities`); берётся из конфига задачи, одно значение на задачу.

### 4.6 Link Resolver
- Сопоставляет сырую wiki-ссылку (`RawLink`, текст вида `path/to/file|alias`) с узлом графа.
- Если целевой файл **входит** в набор, собранный Source Collector — связывается с существующим узлом.
- Если целевой файл **не входит** в набор (внешняя ссылка) — поведение конфигурируется на уровне задачи:
  `on_unresolved: skip | stub` (по умолчанию `skip` — ребро не создаётся, событие логируется как warning).
- Если файл, на который ссылаются, не существует физически — всегда `skip` + warning (это не настраивается).

### 4.7 Graph Builder
- Собирает `Graph { nodes: Node[], edges: Edge[] }` для задачи из результатов 4.3–4.6.
- `Node { id, label, subpath, source_file }`
- `Edge { from_id, to_id, filter_name, style }`
- Дополнительно считает **per-node content hash** = hash(frontmatter-полей, использованных
  как метаданные, + отсортированный список сырых ссылок узла) — используется Cache Manager
  и Diff Engine для определения, что реально изменилось.

### 4.8 Cache Manager
Кэш на задачу хранится в `--cache-dir` (по умолчанию `.cache/diagram-renderer/<task-id>.json`)
и содержит: хэш набора файлов, per-node content hash каждого узла на момент последнего успешного
рендера, и последние известные координаты (x, y, width, height) каждого узла.

Проверка при запуске (если не передан `--force`):
1. Собрать файлы (4.3), посчитать **хэш набора файлов** (пути + mtime или content-hash файлов).
   Если совпадает с сохранённым в кэше — **задача пропускается полностью**, файл результата не трогается.
2. Если хэш набора файлов отличается — построить граф (4.4–4.7), посчитать per-node content hash
   для каждого узла и сравнить с кэшем:
   - Узлы с неизменным hash — их сохранённые координаты переносятся как есть (Layout Engine их не трогает).
   - Узлы новые / с изменившимся hash — передаются в Layout Engine для расчёта позиции.
   - Узлы, исчезнувшие из графа — удаляются из результата и из кэша.
3. После успешной записи результата — кэш перезаписывается новым набором хэшей и позиций
   (включая позиции, которые реально расставил Obsidian, **если** приложение умеет их прочитать
   обратно из существующего `.canvas`-файла перед перезаписью — см. 4.9).

### 4.9 Diff Engine
- Перед расчётом layout сравнивает текущий граф с состоянием **фактического файла результата**
  (не только с кэшем): если пользователь вручную подвинул узлы в Obsidian, `.canvas`-файл на диске
  — источник истины по позициям, кэш — только по хэшам для быстрой проверки "ничего не изменилось".
- Итог работы Diff Engine — три списка: `added`, `removed`, `unchanged` (с уже известными координатами).

### 4.10 Layout Engine (pluggable, интерфейс)
```
class LayoutEngine:
    def place(self, graph: Graph, fixed_positions: dict[node_id, Rect]) -> dict[node_id, Rect]:
        """Возвращает координаты для узлов, отсутствующих в fixed_positions;
        не должен менять координаты уже присутствующих в fixed_positions узлов."""
```
- Реализация v1: слоистая раскладка (Sugiyama-подобная) — послойное распределение по
  длине пути зависимостей + расстановка внутри слоя (barycenter-эвристика для уменьшения
  пересечений). Реализуется на чистом Python, без внешних системных зависимостей (Graphviz и т.п.).
- Новые узлы располагаются в свободном пространстве рядом со своими связями, не пересчитывая
  позиции уже существующих (см. 4.9) узлов.
- **Предположение, требует подтверждения:** слоистая раскладка предполагает, что граф —
  ацикличный (DAG). При обнаружении цикла — цикл логируется как warning, и обратное ребро,
  вызывающее цикл, временно исключается только из расчёта слоёв (не из итоговой диаграммы).

### 4.11 Format Writer (pluggable, интерфейс)
```
class FormatWriter:
    def write(self, graph: Graph, positions: dict[node_id, Rect], destination: Path) -> None: ...
```
- Реализация v1: `ObsidianCanvasWriter` — пишет JSON по схеме JSON Canvas
  (см. `skills/dotnet/architecture/artifacts/solutions/🧩validated/Untitled.canvas` как референс):
  - node: `{ id, type: "file", file, x, y, width, height, subpath? }`
  - edge: `{ id, fromNode, fromSide, toNode, toSide, color?, label? }`
  - `id` узла в Canvas — стабильно выводится из `Node.id` (не пересоздаётся при каждом запуске,
    иначе Obsidian потеряет связь узла с его позицией).
  - Запись — **не полная перезапись файла с нуля**, а merge: узлы/рёбра, отсутствующие в новом
    графе, удаляются; существующие — обновляются только по полям, кроме позиции/размера, если
    узел попал в `unchanged` (4.9).

## 5. Поток выполнения (на одну задачу)

```
1. Source Collector: собрать файлы по source.include/exclude
2. Cache Manager: хэш набора файлов == кэш? -> да: STOP (файл результата не трогается)
3. Link Filter(s): извлечь сырые ссылки по каждому фильтру, для каждого файла
4. Metadata Extractor: извлечь id/label/subpath для каждого файла
5. Link Resolver: сопоставить сырые ссылки с узлами графа (или skip/stub)
6. Graph Builder: собрать Graph + per-node content hash
7. Diff Engine: сравнить с текущим destination-файлом -> added/removed/unchanged
8. Layout Engine: рассчитать координаты для added, сохранить координаты unchanged как есть
9. Format Writer: смержить и записать destination-файл
10. Cache Manager: сохранить новый хэш набора файлов + per-node hash + позиции
```

## 6. Конфигурация

### 6.1 Формат конфига (пример)
```yaml
cache_dir: .cache/diagram-renderer

tasks:
  - id: dotnet-solutions-depends-on
    source:
      include:
        - "skills/dotnet/architecture/artifacts/solutions/**/*.skill.md"
      exclude: []
    metadata:
      label_field: name
      subpath: "#Capabilities"
    links:
      - name: depends_on
        type: frontmatter_field
        field: depends_on
        on_unresolved: skip
        style:
          color: "4"
          label: "depends on"
    layout:
      engine: layered
      direction: LR
    output:
      format: obsidian_canvas
      destination: "skills/dotnet/architecture/artifacts/solutions/🧩validated/dependencies.canvas"
```

### 6.2 CLI для разовой задачи (эквивалент одной записи из tasks)
```
diagram-renderer render \
  --include "skills/dotnet/architecture/artifacts/solutions/**/*.skill.md" \
  --link-field depends_on \
  --label-field name \
  --subpath "#Capabilities" \
  --layout layered --layout-direction LR \
  --format obsidian_canvas \
  --output "skills/dotnet/architecture/artifacts/solutions/🧩validated/dependencies.canvas"
```

### 6.3 CLI для пакета задач
```
diagram-renderer render --config diagrams.yaml [--task-id dotnet-solutions-depends-on] [--force]
```

## 7. Модель данных (сводно)

```
RawLink       { text: str }                                  # сырой текст wiki-ссылки до резолва
NodeMetadata  { id: str, label: str, subpath: str | None }
Node          { id, label, subpath, source_file, content_hash }
Edge          { from_id, to_id, filter_name, style }
Graph         { nodes: Node[], edges: Edge[] }
Rect          { x: float, y: float, width: float, height: float }
EdgeStyle     { color: str | None, label: str | None }
RenderTask    { id, source, metadata, links: LinkFilterConfig[], layout, output }
```

## 8. Обработка ошибок и граничные случаи

- Файл без нужного frontmatter-поля для фильтра — просто не даёт рёбер по этому фильтру (не ошибка).
- Файл с невалидным YAML frontmatter — пропускается с warning, не останавливает всю задачу.
- Ссылка на файл вне набора задачи — согласно `on_unresolved` (по умолчанию `skip`).
- Ссылка на несуществующий файл — всегда warning + skip.
- Цикл зависимостей — warning, ребро временно исключается только из расчёта слоёв layout (см. 4.10).
- Пустой набор файлов после фильтра — задача завершается с warning, результат не создаётся/не трогается.
- Повреждённый/невалидный существующий `.canvas`-файл в destination (не наш формат или битый JSON) —
  задача останавливается с явной ошибкой, **не перезаписывает** файл молча (риск потери ручной правки).

## 9. Предположения, требующие подтверждения

1. Кэш и файл результата могут разойтись (кэш есть, файла нет, или наоборот) — в этом случае
   приоритет у фактического файла результата (Diff Engine читает его напрямую), кэш только
   ускоряет "ничего не изменилось" на шаге 2 потока (раздел 5).
2. Хэш набора файлов = хэш от (relative path + mtime) каждого файла, а не от полного содержимого —
   компромисс скорости/точности. Если нужна 100% точность при поддельных mtime — можно перейти
   на content-hash, но это дороже при большом числе файлов.
3. Слоистая раскладка (layered/Sugiyama) выбрана как встроенная реализация без внешних
   зависимостей (см. обсуждение в этом же тред: Graphviz дал бы лучшее качество, но требует
   системного бинарника `dot`, которого нет на машине по умолчанию).
4. Стиль ребра (`color`/`label`) фиксируется на уровне фильтра в конфиге, а не вычисляется динамически.

## 10. Критерии приёмки

- [ ] `diagram-renderer render --config diagrams.yaml` строит `.canvas`-файл(ы) для всех задач в конфиге.
- [ ] Повторный запуск без изменений в исходных файлах не изменяет mtime/содержимое результата.
- [ ] Изменение `depends_on` в одном файле приводит к обновлению только связанных с ним рёбер/узлов;
      позиции остальных узлов в `.canvas` не меняются.
- [ ] Ручное перемещение узла в Obsidian не откатывается следующим запуском, если сам узел не изменился.
- [ ] Добавление нового `*.skill.md` файла с `depends_on` на существующий узел добавляет новый узел
      рядом с существующими, не переставляя их.
- [ ] Один и тот же набор файлов, обработанный дважды подряд, даёт идентичный `.canvas` (детерминированность).
- [ ] Задача с несколькими фильтрами ссылок рисует рёбра разных фильтров разным стилем на одном холсте.
- [ ] Ошибка в одной задаче пакета не прерывает выполнение остальных задач конфига.
